# 多供应商 LLM 路由、解说分层与失败治理方案（v1.0.5）

> 日期：2026-08-24  
> 状态：已实施，待真实付费请求验收  
> 范围：阶段 3 视觉理解、阶段 5 解说稿生成、LLM 客户端、模型参数配置  
> 兼容策略：不兼容旧环境变量和旧 `models.yaml` 结构；一次性切换，避免新旧命名并行留坑。

---

## 1. 背景

当前项目所有 LLM 请求都通过 `src/mmm/llm.py` 发送。客户端从全局变量读取网关配置：

```bash
OPENCODE_ZEN_BASE_URL
OPENCODE_ZEN_API_KEY
```

这个命名和结构在项目早期可用，但存在五个问题：

1. **供应商语义绑定过强**：`OPENCODE_ZEN_*` 让配置看起来只能使用 Opencode Go。实际上后续可能混搭 DeepSeek 官方 API、Kimi/Moonshot 官方 API、Opencode Go 或其他 OpenAI 兼容服务。
2. **阶段无法独立选型**：阶段 5 当前只有一个 `MMM_NARRATE_MODEL`，分片草稿和最终融合都使用同一个模型。希望低能力模型负责分片素材整理，高能力模型只负责最终写作，以降低高能力模型的调用次数。
3. **模型名不是稳定配置键**：`config/models.yaml` 目前按模型名匹配请求行为。不同服务商可能提供相同或相近的模型名，但字段行为、token 上限、温度策略和扩展参数不同。继续用模型名做唯一配置键，会造成同名不同行为的配置冲突。
4. **分片与融合使用同一份叙事风格**：`stage_narrate.py` 的 `_NARRATIVE_STYLE` 同时约束 LOW 分片和 HIGH 融合。这会让 LOW 模型过早关注文笔，反而可能为了表达顺滑而牺牲角色名、因果关系和关键台词的完整性。
5. **统一重试策略不适合成本差异明显的调用**：当前客户端按模型 profile 统一重试网络和服务端错误。HIGH 融合是全流程最贵的写作调用，静默自动重试会放大费用，并且超时或连接中断时无法确认服务端是否已经开始生成并计费。

同时，阶段 5 已有分层生成流程：

| 场景 | 当前流程 | 当前昂贵模型请求数 |
|---|---|---:|
| 单视频 | timeline → 一次生成 narration 和台词引用 | 1 |
| 多视频 | 每个视频生成分片草稿 → 全局融合 → 本地引用重映射 | N + 1 |

多视频流程的分片草稿并不必须由高能力写作模型完成。更合理的成本结构是：

```text
N 个视频 → LOW 模型生成结构化剧情节拍
全部分片 → HIGH 模型写最终解说稿
程序本地映射引用 → 最终 narration
```

这样昂贵模型请求数从 `N + 1` 降低到 `1`，总逻辑请求数仍是 `N + 1`，但大部分输入消费转移到低成本模型。

## 2. 目标与非目标

### 目标

1. 移除全局 `OPENCODE_ZEN_*` 依赖，改为每个 LLM 使用独立 endpoint。
2. 阶段 5 拆分为两个固定路由：
   - `narrate_low`：素材节拍抽取；
   - `narrate_high`：单视频终稿和多视频融合终稿。
3. 阶段 3 视觉理解拆分为独立路由：
   - `vision`；
   - 不再复用解说模型的全局网关配置。
4. `.env` 中每个路由显式声明：
   - profile 选择器；
   - 实际模型 ID；
   - BASE URL；
   - API KEY。
5. `config/models.yaml` 不再按线上模型名作为顶层配置键，改为按供应商接入 profile 配置字段行为。
6. 保持阶段 5 现有引用防伪机制：
   - LOW 模型输出结构化剧情节拍和台词行 ID；
   - HIGH 模型输出 beat 引用；
   - `_remap_beat_refs()` 在本地确定性映射回真实台词行 ID；
   - 不新增“事后让低能力模型补引用”的调用。
7. 支持断点续跑：LOW 分片缓存必须同时校验模型、profile、输出 schema、LOW prompt fingerprint 和分片 timeline fingerprint。
8. 拆分阶段 5 提示词职责：
   - LOW 使用素材抽取指令，优先保证事实、因果、人物和关键台词完整；
   - HIGH 使用叙事风格指令，负责口播节奏、人称、留白和最终文风；
   - 防止 LOW 为了文笔流畅而提前丢掉 HIGH 需要的信息。
9. 建立按 route 区分的重试策略：
   - `narrate_high` 关闭自动重试；
   - LOW 和 vision 只保留有限瞬态重试；
   - 所有业务级失败，例如空响应和 JSON 解析失败，都不自动重试。
10. 建立 LLM 调用日志和失败产物留存机制，保证 HIGH 不重试后用户仍能定位问题。
11. 提供 `narrate --dry-run` 费用与请求计划预检，在任何真实请求前展示将发生的 LOW/HIGH 调用量。

### 非目标

1. 本版本不推翻现有终稿审美方向，但会把 `_NARRATIVE_STYLE` 改造并收敛为 HIGH 专用叙事风格；LOW 新增独立的素材抽取规范。
2. 本版本不引入新的第三方依赖。
3. 本版本不改变阶段 6 选片、闸口、EDL 和渲染流程。
4. 本版本不做旧变量自动迁移层；只允许一次性修改 `.env`。
5. 本版本不实现非 OpenAI compatible 协议。所有初始 profile 都假定服务暴露 OpenAI compatible `/chat/completions`；未来如需 Anthropic、Gemini 原生协议，再增加协议适配器。

## 3. 核心设计

### 3.1 四个概念分离

v1.0.5 把过去混在一起的配置拆成四层：

| 层 | 存放位置 | 解决的问题 | 示例 |
|---|---|---|---|
| Route / 路由 | 代码中的固定常量 | 表示流水线中的角色，不随供应商变化 | `narrate_low`、`narrate_high`、`vision` |
| Endpoint / 端点 | `.env` | 表示实际请求地址、密钥和线上模型 ID | `MMM_NARRATE_HIGH_BASE_URL` |
| Profile / 供应商适配 | `config/models.yaml` | 表示某个接入方式的行为差异 | `deepseek_official`、`kimi_official` |
| Task policy / 任务策略 | `config/models.yaml` 的 route 配置 | 表示该阶段允许的 token、温度、并发等策略 | 分片预算、融合预算、视觉并发 |

关键原则：

```text
Route 回答“这次调用属于哪个流水线角色”。
Endpoint 回答“请求发到哪里、用哪个模型、用什么密钥”。
Profile 回答“这家服务的字段和行为怎么适配”。
Task policy 回答“这个阶段的预算、温度和并发是多少”。
```

线上模型名只出现在请求 payload 中，不再作为唯一配置键。

### 3.2 提示词与中间产物的职责分离

阶段 5 从“两次写稿”调整为“证据抽取 + 终稿写作”。

#### LOW：证据完整层

`narrate_low` 的目标不是写出漂亮解说稿，而是在有界输入内整理完整故事骨架。其指令命名为：

```python
_LOW_EXTRACTION_INSTRUCTIONS
```

LOW 必须保留：

1. 事件因果和结果；
2. 人物关系和身份变化；
3. 关键反转、冲突、悬念；
4. 重要台词原文；
5. 每个事件对应的片段内台词行 ID；
6. 剧情跳跃和不确定信息标记；
7. 角色在素材中的规范名。

LOW 必须忽略的约束包括：

1. 句首是否以人名开头；
2. 中文口播节奏；
3. 画面感收束；
4. 解说温度；
5. 是否适合主播朗读；
6. 破折号和副标题等成稿文体规则。

LOW 可以概括过程性对话，但不做创造性删减。宁可输出较多候选节拍，也不能为了让文字更干净而提前丢弃潜在反转。

#### HIGH：叙事表达层

现有 `_NARRATIVE_STYLE` 收敛为：

```python
_HIGH_NARRATIVE_STYLE
```

它只在 `narrate_high` 的单视频终稿和多视频融合 prompt 中注入。HIGH 负责：

1. 把剧情节拍组织成沉浸式故事；
2. 统一玩家视角和人称；
3. 决定直接引语和间接叙述的取舍；
4. 控制口播节奏、悬念、温度和画面感收束；
5. 合并重复节拍并裁剪到目标时长；
6. 输出可被程序映射回真实台词行的引用。

素材边界规则同时保留在两层：LOW 不得虚构素材外事实，HIGH 也不得超出 LOW 提供的证据范围补剧情。

#### 中间产物采用剧情节拍

LOW 分片产物从“粗糙解说稿”升级为结构化剧情节拍：

```json
{
  "video_id": "gs-16-p1",
  "chunk_id": "chunk_001",
  "segment_id": "gs-16-p1::chunk_001",
  "beats": [
    {
      "id": 1,
      "summary": "主角一行进入遗迹，发现封印装置。",
      "characters": ["主角", "派蒙"],
      "cause": "前一段线索指向遗迹深处。",
      "effect": "引出解锁仪式和守卫出现。",
      "key_quotes": [
        {
          "speaker": "派蒙",
          "text": "这个东西看起来不太妙。",
          "line_id": 128
        }
      ],
      "related_line_ids": [126, 127, 128],
      "importance": "core",
      "confidence": "high"
    }
  ]
}
```

字段约定：

| 字段 | 说明 |
|---|---|
| `segment_id` | LOW 逻辑分片全局唯一 ID，格式为 `{video_id}::{chunk_id}`，供 HIGH 引用 |
| `id` | 片段内 beat ID，供 HIGH 引用 |
| `summary` | 中性事件摘要，不做文学化润色 |
| `characters` | 素材中的规范角色名 |
| `cause` / `effect` | 因果链，未知时留空或标注 unknown |
| `key_quotes` | 关键台词原文及其行 ID |
| `related_line_ids` | 该 beat 覆盖的片段内台词行 ID |
| `importance` | `core` / `supporting` / `background` |
| `confidence` | LOW 对该节拍事实完整度的自评 |

HIGH 不再引用“粗糙解说稿句号”，改为引用 `beat_id`。融合输出先使用：

```json
{
  "id": 1,
  "text": "终稿解说句。",
  "related_beat_ids": [
    {
      "segment_id": "gs-16-p1::chunk_001",
      "beat_id": 1
    }
  ]
}
```

随后 `_remap_beat_refs()` 在本地把 `related_beat_ids` 展开成真实台词行：

```json
{
  "id": 1,
  "text": "终稿解说句。",
  "related_line_ids": [
    {
      "video_id": "gs-16-p1",
      "line_id": 126
    },
    {
      "video_id": "gs-16-p1",
      "line_id": 128
    }
  ]
}
```

这个结构调整比继续让 LOW 输出粗糙解说稿更稳：LOW 不需要考虑文风，HIGH 也能看到因果、角色、重要原文和覆盖区间。

引用校验规则：

1. `related_beat_ids` 为空、缺少 `segment_id`、缺少 `beat_id`，或引用了当前 LOW 分片中不存在的 beat，均视为 schema 校验失败；该失败不可自动重试，并保留 HIGH 原始响应。
2. 同一终稿句重复引用同一个 beat 时，由 `_remap_beat_refs()` 本地去重。
3. 单条终稿句引用超过 8 个 beat 时不硬失败、不自动截断引用；保留完整引用并在闸口 1 输出提示，要求人工确认该句是否过度概括。
4. 程序不得根据文案内容自动补写、猜测或扩展引用。引用必须来自 HIGH 输出，并能在 LOW 分片中找到唯一对应。

### 3.3 重试与资金保护

重试策略由 route 决定，不由供应商 profile 自动决定。原因是同一个服务商可能同时承载便宜分片和昂贵终稿，成本控制必须挂在流水线角色上。

| route | `max_retries` | 最大 HTTP 尝试次数 | 可自动重试 | 禁止自动重试 | 设计理由 |
|---|---:|---:|---|---|---|
| `narrate_low` | 1 | 2 | `429`、`500`、`502`、`503`、网络中断、响应中断 | `400`、`401`、`403`、`404`、空内容、JSON 解析失败 | 单次成本低，但要防止 N 个分片放大费用 |
| `narrate_high` | 0 | 1 | 无 | 全部错误，包括网络类异常和空内容 | 最贵调用必须显式失败给用户，避免静默双倍计费风险 |
| `vision` | 1 | 2 | `429`、`500`、`502`、`503`、网络中断、响应中断 | `400`、`401`、`403`、`404`、持续解析失败 | 单镜头成本低且数量多，保留一次瞬态容错 |

语义约定：

```text
max_retries = 0 表示只发一次请求；
max_retries = 1 表示首次失败后最多再试一次；
空内容、非法 JSON、schema 校验失败属于业务失败，任何 route 都不自动重试；
HTTP 403 通常表示鉴权、权限或 WAF 配置问题，不作为瞬态错误重试。
```

HIGH 失败后的恢复方式是人工决策：

1. 查看 `llm_calls.jsonl` 和失败产物；
2. 确认是否修改配置、prompt 或 token 预算；
3. 用户再次执行命令；
4. 多视频模式下有效 LOW 分片继续命中缓存，因此重跑通常只重复 HIGH；
5. 单视频模式没有 LOW 成本，但会重新发起唯一的一次 HIGH。

测试、实验、验证或费用预估类操作必须先执行 `--dry-run`。只有使用者明确要求真实连通性验证或完整生成时，才允许发起付费请求。

### 3.4 LLM 调用日志

`llm.chat()` 不再只返回字符串，改为返回结构化结果：

```python
@dataclass(frozen=True)
class LLMCallResult:
    content: str
    route: str
    profile_id: str
    model: str
    attempt: int
    duration_ms: int
    http_status: int | None
    finish_reason: str | None
    usage: dict | None
    response_chars: int
    response_preview: str
```

每次尝试写入一条 JSONL 日志：

```json
{
  "ts": "2026-08-24T12:00:00+08:00",
  "route": "narrate_high",
  "profile": "kimi_official",
  "model": "kimi-k3-official-id",
  "base_url_host": "api.moonshot.cn",
  "label": "fuse:task-hd-p5",
  "attempt": 1,
  "max_retries": 0,
  "will_retry": false,
  "prompt_chars": 18234,
  "estimated_prompt_tokens": 12156,
  "max_tokens": 65536,
  "temperature_mode": "omit",
  "request_hash": "sha256:...",
  "http_status": 200,
  "duration_ms": 48210,
  "finish_reason": "stop",
  "usage": {
    "prompt_tokens": 12001,
    "completion_tokens": 6011,
    "total_tokens": 18012
  },
  "response_chars": 14200,
  "response_preview": "{\"narration\":[...]}",
  "response_hash": "sha256:...",
  "error_type": null,
  "error_message": null
}
```

日志文件默认写入：

```text
logs/llm_calls.jsonl
```

`logs/llm_calls.jsonl` 是项目级唯一调用账本，不按 task 拆分。写入方式为追加一行完整 JSON，并在进程内用锁串行化；同进程内的 LOW 并发、vision 并发和 HIGH 调用都不得写出交错行。失败原始响应只放入 task 目录，不放入 JSONL。

`logs/` 与 `tasks/` 均为本地私有运行产物，不进入 Git。若未来需要用真实响应构造测试数据，必须先人工脱敏并复制到专门的测试资产目录，不得直接提交运行日志或失败响应。

日志红线：

1. 不记录 `API_KEY` 和 `Authorization`；
2. BASE URL 只记录 host 和 path，不记录 query 中的凭据；
3. 不落盘完整 prompt；
4. 响应 preview 默认截断到 500 字符；
5. 服务商错误 body 截断后再记录。

除 JSONL 外，HIGH 或 LOW 返回非空但无法解析为合法 schema 时，应保存原始响应用于人工修复：

```text
tasks/{task_id}/llm_failures/{YYYYMMDD_HHMMSS}_narrate_high.txt
tasks/{task_id}/llm_failures/{YYYYMMDD_HHMMSS}_narrate_low_{video_id}.txt
```

终端错误必须包含三件事：

```text
失败 route
日志文件路径
失败响应文件路径（如有）
```

### 3.5 环境变量设计

`.env.example` 目标结构如下：

```bash
# 阶段5 素材节拍抽取 / 分片素材整理
MMM_NARRATE_LOW_PROFILE=
MMM_NARRATE_LOW_MODEL=
MMM_NARRATE_LOW_BASE_URL=
MMM_NARRATE_LOW_API_KEY=

# 阶段5 单视频终稿 / 多视频融合终稿
MMM_NARRATE_HIGH_PROFILE=
MMM_NARRATE_HIGH_MODEL=
MMM_NARRATE_HIGH_BASE_URL=
MMM_NARRATE_HIGH_API_KEY=

# 阶段3 视觉理解
MMM_VISION_PROFILE=
MMM_VISION_MODEL=
MMM_VISION_BASE_URL=
MMM_VISION_API_KEY=

```

删除以下旧变量：

```bash
OPENCODE_ZEN_BASE_URL
OPENCODE_ZEN_API_KEY
MMM_NARRATE_MODEL
```

新增 `*_PROFILE` 的原因：仅凭模型名无法可靠判断供应商行为。例如同一个 Kimi 模型可能分别通过 Opencode Go 和 Moonshot 官方 API 访问，两者的超时、字段兼容性和扩展参数可能不同。profile 是显式选择器，避免根据 URL 字符串猜测供应商。

推荐 profile 命名：

| profile | 含义 |
|---|---|
| `opencode_go` | 当前 Opencode Go 接入方式 |
| `deepseek_official` | DeepSeek 官方 OpenAI compatible API |
| `kimi_official` | Kimi / Moonshot 官方 OpenAI compatible API |

实际模型 ID 必须以供应商控制台为准，不硬编码到 Python 代码中。

### 3.6 `config/models.yaml` 新结构

目标结构分为 `defaults`、`profiles`、`routes` 三部分。

```yaml
defaults:

  temperature_mode: passthrough

  input_context_tokens: 131072
  safety_margin_tokens: 8192
  timeout_seconds: 300
  retry_backoff_seconds: 5
  min_interval_seconds: 0.5
  capabilities:
    - text
  request_extra: {}

profiles:
  opencode_go:
    protocol: openai_chat_completions
    temperature_mode: passthrough
    max_tokens_field: max_tokens
    input_context_tokens: 1000000
    safety_margin_tokens: 16384
    timeout_seconds: 300
    retry_backoff_seconds: 5
    capabilities:
      - text
      - image

  deepseek_official:
    protocol: openai_chat_completions
    temperature_mode: passthrough
    max_tokens_field: max_tokens
    input_context_tokens: 131072
    safety_margin_tokens: 8192
    timeout_seconds: 300
    retry_backoff_seconds: 5
    capabilities:
      - text

  kimi_official:
    protocol: openai_chat_completions

    safety_margin_tokens: 16384

    retry_backoff_seconds: 5

      - text

routes:
  narrate_low:
    defaults:
      temperature: 0.6
      max_tokens: 32768
      narration_segment_workers: 1
      max_retries: 1
      retryable_status_codes: [429, 500, 502, 503]
      retry_network_errors: true

  narrate_high:
    defaults:
      temperature: 0.4
      max_tokens: 65536
      max_retries: 0
      retryable_status_codes: []
      retry_network_errors: false

  vision:
    defaults:
      max_tokens: 1500
      max_retries: 1
      retryable_status_codes: [429, 500, 502, 503]
      retry_network_errors: true
```

字段语义：

| 字段 | 层级 | 说明 |
|---|---|---|
| `protocol` | profile | 请求协议适配器。v1.0.5 只实现 `openai_chat_completions`。 |
| `temperature_mode` | profile | `passthrough` 表示跟随调用方；`omit` 表示不发送；数值表示强制覆盖。 |
| `max_tokens_field` | profile | 允许不同服务使用 `max_tokens` 或 `max_completion_tokens` 等字段。 |
| `input_context_tokens` | profile | 该接入方式的可用输入上下文窗口，以供应商文档或控制台为准。 |
| `safety_margin_tokens` | profile | 吸收本地 token 估算误差与服务端计入差异的安全边距。 |
| `capabilities` | profile | 能力声明。`vision` route 必须包含 `image`。 |
| `timeout_seconds` | profile | 单次 HTTP 超时。 |
| `retry_backoff_seconds` | profile | 指数退避基数。 |
| `min_interval_seconds` | profile | 同一 profile 的最小请求间隔。 |
| `request_extra` | profile | 服务商专属扩展字段，直接合并进 JSON payload，禁止覆盖协议核心字段。 |
| `routes.*.defaults.max_tokens` | route | 该角色的默认输出预算。 |
| `routes.narrate_low.defaults.narration_segment_workers` | route | 分片并发线程数。 |
| `routes.*.defaults.max_retries` | route | 该角色的最大重试次数；route 值始终覆盖 profile/default。 |
| `routes.*.defaults.retryable_status_codes` | route | 允许自动重试的 HTTP 状态码。 |
| `routes.*.defaults.retry_network_errors` | route | 是否允许重试网络中断、超时和响应中断。 |

合并顺序为：

```text
defaults → profiles[selected_profile] → routes[route]
```

但协议约束拥有更高优先级。例如 profile 设置 `temperature_mode: omit` 时，即使 route 给出建议温度，最终 payload 也不发送 `temperature`。

### 3.7 LLM 客户端改造

`src/mmm/llm.py` 引入显式 endpoint 对象：

```python
@dataclass(frozen=True)
class LLMEndpoint:
    route: str
    profile_id: str
    model: str
    base_url: str
    api_key: str
    profile: ModelProfile
```

新增加载函数：

```python
def load_endpoint(route: str) -> LLMEndpoint:
    """按固定 route 从 .env 读取完整 endpoint，并解析 profile。"""
```

route 与环境变量前缀的映射固定为：

| route | env prefix |
|---|---|
| `narrate_low` | `MMM_NARRATE_LOW_` |
| `narrate_high` | `MMM_NARRATE_HIGH_` |
| `vision` | `MMM_VISION_` |

缺失配置时报错必须包含完整变量名，例如：

```text
缺少 MMM_NARRATE_HIGH_API_KEY（.env 或环境变量）
```

`chat()` 的签名从按模型名字符串调用，改为按 endpoint 调用：

```python
def chat(endpoint: LLMEndpoint, messages: list[dict], *, max_tokens: int) -> LLMCallResult:
    ...
```

payload 组装规则：

```jsonc
{
  "model": "<endpoint.model>",
  "messages": "<调用方传入>",
  "max_tokens": "<受 profile cap 限制后的值>",
  "temperature": "<只有 profile 允许时才发送>"
}
```

如果 profile 定义了 `request_extra`，这些字段最后合并进 payload。保留字段为 `model`、`messages`、`stream`，以及 `max_tokens_field` 声明的输出预算字段；`temperature` 也必须通过 `temperature_mode` 表达。`request_extra` 覆盖任一保留字段时配置解析直接失败。若某服务商要求改变这些核心字段语义，应新增协议适配器，而不是使用 YAML 后门。

`chat_with_image()` 同步改为接收 vision endpoint，不再通过全局配置隐式定位服务。

限速策略从全局单例改为按 `(profile_id, normalized_base_url)` 隔离。同一个供应商入口共享最小间隔，避免并发压垮同一服务商；不同入口互不影响。API KEY 不参与限速键，避免密钥进入运行时状态；模型名也不参与，因为同一入口通常共享服务商配额。

重试判断顺序如下：

```text
1. 读取 route 的 max_retries；
2. 业务级失败立即抛出，并写入日志和失败产物；
3. 判断异常类型是否属于 route 允许的瞬态类型；
4. 判断 HTTP status 是否在 retryable_status_codes 内；
5. 已完成尝试次数小于 max_retries + 1 时才发起下一次请求。
```

## 4. 阶段 5 改造

### 4.1 路由职责

#### 单视频

```text
timeline.json
  → narrate_high
  → narration + related_line_ids
  → narration.json / narration.md
```

单视频不引入 LOW 模型。原因是单视频只需要一次强写作调用，而台词归因必须在写作时同步完成；拆成“先纯文案、后补引用”会增加请求次数并降低引用可靠性。

上下文保护规则：发起 HIGH 调用前必须本地估算 prompt 输入规模。判定公式为：

```text
estimated_prompt_tokens + route.max_tokens + profile.safety_margin_tokens
<= profile.input_context_tokens
```

满足公式时维持单次调用；不满足时不允许截断 timeline，而是按场景将单视频切成多个逻辑分片，内部走“LOW 分片 → 单次 HIGH 融合”。此时“单视频”只表示任务输入形态，不再强制等价于“HIGH 直接读取完整 timeline”。

token 估算使用保守字符启发式，不额外调用 tokenizer 或 LLM：中文字符按约 1 token/字估算，JSON 标点和英文按约 0.75 token/字符估算，并向上取整。估算误差由 `safety_margin_tokens` 吸收；宁可提前分片，也不能为了减少 LOW 请求而截断事实源。

#### 多视频

```text
global_timeline.json
  → 按 video_id 切分
  → 按 LOW 上下文判定生成逻辑分片
  → 每个逻辑分片调用一次 narrate_low
  → narration_segments/{segment_id}.json（story beats）
  → 所有分片调用一次 narrate_high
  → HIGH 输出 related_beat_ids
  → _remap_beat_refs() 本地映射真实台词 ID
  → narration.json / narration.md
```

请求数：

| 场景 | LOW 请求数 | HIGH 请求数 | 本地映射 |
|---|---:|---:|---|
| 单视频 | 0 | 1 | 不需要 |
| 超上下文单视频（按场景切成 N 个逻辑分片） | N | 1 | 需要 |
| 多视频 N 个有效视频、均未触发 LOW 分片 | N | 1 | 需要 |
| 多视频 N 个有效视频、共切成 M 个 LOW 逻辑分片 | M | 1 | 需要 |

分片命中缓存时不发起 LOW 请求。HIGH 终稿也有显式复用闸门：`narration.json` 已存在且其 HIGH profile、model、prompt fingerprint、timeline fingerprint 和 target_minutes 均匹配时，默认跳过 HIGH。

开发验证期不做旧 schema 兼容。真实执行一旦判定机器生成终稿不可复用，会先删除旧 `narration.json` / `narration.md`，再发起重建，避免失败后残留一份看起来可用的旧稿。`_human_edited: true` 是唯一例外：未显式传 `--force` 时直接拒绝执行，不删除、不请求、不覆盖。

LOW 使用与 HIGH 相同的上下文判定公式。单个 `video_id` 未超限时保持一个视频一次 LOW；超过时不截断该视频，而是按场景继续切分为多个逻辑分片。这样常规 20~30 分钟视频不会增加请求，只有接近 LOW 输入上限的高密度长视频才触发额外分片。

### 4.2 执行计划与 `--dry-run`

阶段 5 的计划阶段只读本地文件和配置，不发起 LLM 请求。`narrate --dry-run` 必须输出：

1. 任务输入形态：单视频 / 多视频 / 单视频触发超上下文分片；
2. LOW 逻辑分片总数、缓存命中数、将发起的 LOW 请求数；
3. HIGH 是否会复用现有 `narration.json`，或是否需要 `--force`；
4. 将发起的 HIGH 请求数，正常终稿生成固定为 0 或 1；
5. LOW / HIGH 当前 route、profile、model、`max_retries` 和最大 HTTP attempt 数；
6. HIGH prompt 的保守 token 估算、输出预算、上下文窗口与安全边距；
7. 若不满足上下文公式，列出将触发的场景分片边界；
8. 明确提示：`--dry-run` 未产生任何 LLM 请求和费用。

该模式用于测试、实验、验证、费用预估和修改配置后的影响面检查。项目文档与 Agent 使用规范必须写明：当用户要求“测试、实验、试跑、验证或预估”时，默认先执行 `--dry-run`；真实付费请求必须得到用户明确确认。

### 4.3 LOW 与 HIGH 的职责边界

提示词常量拆分为两组：

```python
_LOW_EXTRACTION_INSTRUCTIONS = """..."""
_HIGH_NARRATIVE_STYLE = """..."""
```

`_LOW_EXTRACTION_INSTRUCTIONS` 只服务分片素材整理，核心要求是：

1. 按时间顺序抽取故事节拍；
2. 从对话和画面索引中还原因果、人物、冲突和反转；
3. 保留关键台词原文，而不是只写转述结论；
4. 为每个 beat 标记 `related_line_ids`；
5. 标记角色规范名、事件重要性和事实置信度；
6. 不使用成稿文笔规则，不追求口播节奏。

`_HIGH_NARRATIVE_STYLE` 由现有 `_NARRATIVE_STYLE` 收敛而来，只服务单视频终稿和多视频融合。现有十条叙事规则中与素材边界相关的约束继续保留；玩家视角、对话取舍、点名分层、句首呼吸、推进留白、配音节奏、温度、合并收束和口播稿文体等纯表达层规则，全部归属 HIGH。

两个 prompt fingerprint 分开计算：

```python
LOW_PROMPT_FP = sha256(
    (_LOW_EXTRACTION_INSTRUCTIONS + _LOW_OUTPUT_SCHEMA_HINT).encode("utf-8")
).hexdigest()[:12]

HIGH_PROMPT_FP = sha256(
    (_HIGH_NARRATIVE_STYLE + _NARRATIVE_EXAMPLE).encode("utf-8")
).hexdigest()[:12]
```

LOW fingerprint 用于分片缓存失效。HIGH fingerprint 写入终稿元数据，便于审计当前稿件由哪版写作指令生成。`narration.json` 作为 HIGH 结果缓存使用；机器稿元数据不匹配时直接失效清理并重建，人工编辑稿必须显式 `--force` 才能覆盖。

注意：HIGH 模型只能看到 LOW 剧情节拍，看不到完整原始 timeline。因此 LOW 的覆盖度决定终稿事实上限。LOW prompt 必须显式禁止“为了摘要漂亮而删除潜在反转”；闸口 1 人工审阅仍是最后兜底。

### 4.4 分片缓存

缓存文件为：

```text
tasks/{task_id}/narration_segments/{segment_id}.json
```

新元数据至少包含：

```json
{
  "video_id": "gs-16-p1",
  "chunk_id": "chunk_001",
  "segment_id": "gs-16-p1::chunk_001",
  "beats": [],
  "_route": "narrate_low",
  "_schema": "story_beats_v1",
  "_profile": "opencode_go",
  "_model": "deepseek-v4-flash",
  "_prompt_fp": "low-prompt-fp",
  "_timeline_fp": "timeline-fp"
}
```

`_timeline_fp` 由当前逻辑分片的 `video_id`、`chunk_id`、chunk 边界、台词行、镜头和关键时间戳计算 SHA-256。`video_id` 本身不编码业务含义，不能作为内容版本号；因此缓存必须绑定事实内容，而不是只绑定视频名称。

缓存复用条件全部满足才跳过请求：

1. `_route == "narrate_low"`；
2. `_schema == "story_beats_v1"`；
3. `_profile == MMM_NARRATE_LOW_PROFILE`；
4. `_model == MMM_NARRATE_LOW_MODEL`；
5. `_prompt_fp == LOW_PROMPT_FP`；
6. `_timeline_fp == 当前逻辑分片 fingerprint`；
7. `segment_id`、`video_id`、`chunk_id` 与当前执行计划一致；
8. `beats` 非空，且每个 beat 的 `related_line_ids` 非空；
9. 所有 `related_line_ids` 与 `key_quotes[].line_id` 均存在于当前逻辑分片的 timeline；
10. 引用中不含 `unvoiced` 台词行。

LOW 响应必须在写入缓存前先通过本地防伪校验。任一校验失败均视为业务失败：不自动重试、保存原始响应、不写入缓存。坏证据不能进入缓存，更不能被 HIGH 继承。

由于旧缓存没有新的 `_route`、`_schema` 和 `_profile` 字段，升级后自然失效。真实执行会删除计划外分片和同名无效分片，再重新生成；dry-run 保持只读，只报告缓存不可复用。该行为符合“不兼容旧结构、避免新旧并行”的要求。

### 4.5 终稿元数据

`narration.json` 的元数据改为结构化字段：

```json
{
  "mode": "segment",
  "target_minutes": 15,
  "routes": ["narrate_low", "narrate_high"],
  "prompt_fingerprints": {
    "narrate_low": "low-prompt-fp",
    "narrate_high": "high-prompt-fp"
  },
  "timeline_fingerprint": "all-segments-fp",
  "evidence_fingerprint": "all-low-segments-fp",
  "_human_edited": false,
  "models": {
    "narrate_low": {
      "profile": "opencode_go",
      "model": "deepseek-v4-flash"
    },
    "narrate_high": {
      "profile": "opencode_go",
      "model": "kimi-k3"
    }
  },
  "narration": []
}
```

单视频模式：

```json
{
  "mode": "oneshot",
  "routes": ["narrate_high"],
  "models": {
    "narrate_low": null,
    "narrate_high": {
      "profile": "kimi_official",
      "model": "kimi-k3"
    }
  },
  "narration": []
}
```

下游阶段只消费 `narration`，不应依赖旧的顶层 `"model"` 字段。

`evidence_fingerprint` 是所有生效 LOW 逻辑分片的聚合指纹，输入包括每个分片的 `segment_id`、schema、LOW profile、LOW model、LOW prompt fingerprint 和 timeline fingerprint。单视频 oneshot 模式该值为空；一旦触发逻辑分片或使用多视频模式，HIGH 复用必须校验该值。

HIGH 结果复用条件为：

1. `narration` 非空且通过结构校验；
2. HIGH profile 和 model 与当前 endpoint 一致；
3. HIGH prompt fingerprint 与当前指令一致；
4. `timeline_fingerprint` 与当前任务一致；
5. `evidence_fingerprint` 与当前 LOW 逻辑分片集合一致；
6. `target_minutes` 与当前命令一致。

`_human_edited` 由人工编辑流程写入。该标记为 `true` 时即使其它条件匹配也默认跳过 HIGH，只允许 `--force` 重生成。

## 6. 配置校验

新增启动期校验，不在请求失败时才发现配置错误。阶段 5 的 endpoint 按执行计划懒加载：普通单视频只加载 `narrate_high`；多视频或触发逻辑分片时才加载 `narrate_low`。`--dry-run` 按计划校验将实际使用的 route，不强制要求用户配置本次不会使用的 LOW。

每个 route 加载时检查：

| 检查项 | 错误处理 |
|---|---|
| route 是否存在于 `models.yaml` | 启动失败 |
| `*_PROFILE` 是否非空 | 启动失败 |
| profile 是否存在于 `profiles` | 启动失败 |
| `*_MODEL` 是否非空 | 启动失败 |
| `*_BASE_URL` 是否非空且为合法 HTTP(S) URL | 启动失败 |
| `*_API_KEY` 是否非空 | 启动失败 |
| vision profile 是否支持 image | 启动失败 |
| protocol 是否已实现 | 启动失败 |
| token 预算是否大于 0 | 启动失败 |
| `input_context_tokens` 和 `safety_margin_tokens` 是否大于 0 | 启动失败 |
| `route.max_tokens + safety_margin_tokens` 是否小于 `input_context_tokens` | 启动失败 |
| `max_retries` 是否大于等于 0 | 启动失败 |
| `retryable_status_codes` 是否为合法 HTTP 状态码集合 | 启动失败 |
| `narrate_high.max_retries != 0` | 启动失败 |
| `request_extra` 是否覆盖协议核心字段 | 启动失败 |

URL 只接受 OpenAI compatible 根地址。客户端继续拼接：

```text
{BASE_URL}/chat/completions
```

因此 BASE URL 不应包含 `/chat/completions`。

## 8. 数据迁移策略

项目处于开发验证阶段，因此不做运行时兼容。迁移规则如下：

1. 本机 `.env` 一次性替换为三组新变量，不保留旧变量，也不生成旧格式备份文件。
2. 将当前可用的 Opencode Go 地址和 KEY 一次性填入三组新变量。
3. 三个 route 的 PROFILE 先统一设为 `opencode_go`。
4. 确认流水线可跑后，再逐 route 切换官方 API。
5. 切换官方 API 时同步更新：
   - `*_PROFILE`；
   - `*_MODEL`；
   - `*_BASE_URL`；
   - `*_API_KEY`；
   - 必要时在 `models.yaml` 新增或调整 profile。

示例：切换单独的 HIGH 写作模型：

```bash
MMM_NARRATE_LOW_PROFILE=deepseek_official
MMM_NARRATE_LOW_MODEL=<DeepSeek 控制台模型 ID>
MMM_NARRATE_LOW_BASE_URL=<DeepSeek OpenAI compatible 根地址>
MMM_NARRATE_LOW_API_KEY=<DeepSeek KEY>

MMM_NARRATE_HIGH_PROFILE=kimi_official
MMM_NARRATE_HIGH_MODEL=<Kimi 控制台模型 ID>
MMM_NARRATE_HIGH_BASE_URL=<Moonshot OpenAI compatible 根地址>
MMM_NARRATE_HIGH_API_KEY=<Moonshot KEY>
```

示例中的尖括号值必须由使用者填写，不得提交真实密钥。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 官方 API 模型 ID 与 Opencode 别名不同 | 请求 404 或模型不存在 | `.env` 只填控制台提供的精确 ID；上线前用 verify 工具小请求验证 |
| 思考型模型输出为空 | narrate 报“返回空内容” | profile 保留足够 token 上限；必要时设置 provider 专属 `request_extra` |
| LOW 模型漏掉关键剧情 | HIGH 无法补回未知事实 | LOW prompt 后续强调剧情节拍完整性；闸口 1 人工审阅兜底 |
| Kimi profile 关闭温度导致文风变化 | 最终稿风格波动 | 在 profile 显式声明 `temperature_mode`，不要靠默认猜测 |
| 视觉模型不支持官方直连图片格式 | vision 请求失败 | profile capability 校验；必要时 vision 继续使用支持图片的服务 |
| 同名模型在不同服务商行为不同 | 参数互相污染 | profile 作为配置键，模型名只进 payload |
| 密钥误提交 | 泄露风险 | 真实 KEY 只放 `.env`；README 和 docs 不出现明文密钥 |
| 分片缓存跨模型或跨内容误用 | 旧风格或旧事实残留 | 缓存校验 route + profile + model + prompt fingerprint + timeline fingerprint |
| LOW 输出过度结构化导致语义压扁 | 关键原文和语气丢失 | `key_quotes` 强制保留爆点台词原文；必要时提高相关 beat 的 importance |
| HIGH 禁止重试后瞬态故障需要人工介入 | 流水线停在阶段 5 | 结构化日志和失败响应留存；多视频 LOW 缓存保证重跑只重复 HIGH |
| 重复执行命令造成 HIGH 重复计费 | 误操作放大费用 | 匹配的 `narration.json` 默认复用；重生成必须 `--force` |

## 12. 验收标准

v1.0.5 完成必须满足以下全部条件：

1. 源码、配置模板和 README 不再出现 `OPENCODE_ZEN_*`。
2. 源码和配置模板不再出现单一 `MMM_NARRATE_MODEL`。
3. `narrate_low`、`narrate_high`、`vision` 三个 route 可独立配置模型、URL 和 KEY。
4. 多视频解说只调用一次 HIGH 模型做融合。
5. 台词引用由 HIGH 模型输出 beat 引用并由本地程序重映射为真实台词行 ID，不新增弱模型补引用链路。
6. `models.yaml` 不再以线上模型名作为顶层配置键。
7. 不同供应商的同名模型可以通过不同 profile 隔离参数。
8. 缺失环境变量时能准确定位到具体变量名。
9. 分片缓存能因 profile、model、prompt fingerprint 或 timeline fingerprint 变化自动失效。
10. vision 请求使用独立的 `vision` route，不再依赖全局 Opencode 配置。
11. LOW prompt 不再包含口播文风规则；HIGH prompt 承担全部终稿审美约束。
12. LOW 中间产物采用 `story_beats_v1`，并保留角色、因果、重要原文和台词行引用。
13. `narrate_high` 的最大 HTTP 尝试次数固定为 1。
14. 匹配的 HIGH 终稿默认跳过，重新生成必须 `--force`；人工编辑稿同样受保护。
15. `--dry-run` 能准确输出 LOW/HIGH 调用计划，且不产生任何 LLM 请求、日志或产物变更。
16. 每次 LLM attempt 都有 JSONL 日志；非空但无法解析的响应有独立失败文件。
17. 日志和失败产物中不含 API KEY 或完整 Authorization header。
