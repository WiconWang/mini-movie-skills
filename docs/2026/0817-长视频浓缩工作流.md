# 长视频浓缩工作流 · 技术设计文档

> 日期：2026-08-17
> 状态：设计稿 v2（已定稿，待开发）

---

## 1. 背景与目标

将几小时长的长视频（剧情、实况、赛事、课程等），自动浓缩为 **十几分钟的解说短视频**。

### 旧方案及其根本缺陷

旧流程：提取音频 → ASR 转文字（带秒数）→ LLM 总结故事 → LLM 为故事每句**模糊匹配台词**拿时间 → 按时间裁切拼接。

三个结构性缺陷：

1. **锚点错误**：整条链以 ASR 文本为唯一索引。ASR 失真（尤其专有名词）→ 匹配失败 → 全流程崩塌。
2. **无视觉理解**：不看画面，匹配到的镜头可能完全不合适。
3. **静默段不可见**：无台词的过场动画（恰恰是画面质量最高的部分）在索引中不存在，永远无法被选中。

### 核心设计原则（第一性原理）

| 原则 | 说明 |
|------|------|
| **台词是铁证，ASR 只是钟** | 内容以准确台词为准；ASR 的唯一职责是提供时间戳。ASR 错的是文字，时间戳极少错。 |
| **先理解，再写稿，最后找画面** | 与人类剪辑师的工作顺序一致。解说稿生于完整时间轴，引用精确时间区间，不做模糊文本匹配。 |
| **镜头是逻辑单位，不是裁切单位** | 镜头只存在于元数据 JSON 中，用于理解和打标签；最终裁切以台词行/解说句的时间区间为准。 |
| **文件只在必须时诞生** | 原视频全程不动；帧图片是喂模型的消耗品；视频片段仅在合成阶段临时切出。任何一步返工只需重算元数据。 |
| **相对时间轴铁律** | 全管线禁止出现「成片第 X 秒」这种绝对时间。一切定位用 `(video_id, 本地时间)`，成片时间轴由 EDL 片段列表在渲染时累积求和——插入/删除/改时长导致后续自动后移，零成本。 |

## 2. 物料与产出

### 输入物料

物料格式契约详见 **[0817-物料规范.md](./0817-物料规范.md)**（爬取/整理工具按此产出，管线按此消费）。

| 物料 | 说明 |
|------|------|
| 长视频 | 几小时，含画面与语音。**一个成片任务可对应一个或一组视频**（多视频按顺序同属一个章节） |
| 完整准确的台词/文稿 | 无时间信息，按内容顺序排列（剧本、讲稿、字幕文件等）。多视频任务可为**一份横跨全部视频的完整台词**，无需人工拆分 |
| 通用/特殊片头 | 固定视频文件，按系列配置 |
| BGM 素材 | 多个背景音乐文件，按清单顺序铺设 |

### 产出

成片结构 = **通用片头 + 本任务特殊片头 + 解说稿正片**：

- 正片：TTS 解说配音 + BGM 音轨 + 按画面质量优先级选取的原视频片段（默认弃原声，高光插入段除外）
- 双通道导出：ffmpeg 直出 MP4（默认）/ 剪映草稿（人工精修）

### 画面类型分级（选片优先级 E → A）

**分级体系是类型适配层，可按内容类型配置。** 下表以剧情类视频为默认示例：

| 级别 | 类型 | 特征 | 优先级 |
|------|------|------|--------|
| **E** | 标志性过场（黑/白屏边界） | 有明确黑屏/白屏淡入淡出边界，无界面元素，电影化演出 | 最高 |
| **D** | 无台词运镜画面 | 无台词覆盖，镜头切换/主体动作，无界面元素 | 高 |
| **C** | 高动态画面 + 台词 | 有台词覆盖，画面高动态（动作、特效、快节奏） | 中 |
| **B** | 对话画面（有运镜） | 有台词，主体基本静止但有运镜/动作 | 低 |
| **A** | 静态对话 | 有台词，静态镜头、头像/固定机位 | 最低 |

**类型适配说明**：接入新内容类型时，重新定义分级表而非复用本表。例如：赛事集锦可将「进球/得分瞬间」提为最高级；课程视频可将「板书/演示画面」提为最高级。检测信号（黑白屏、UI 检测、运动强度、台词覆盖）是通用的，变的只是**信号→级别→优先级**的映射配置。命名模板、片头组合、画面变换参数同属类型适配层。

## 3. 总体架构

```
 准确台词 ────────┐
                  ├─→ 阶段2: ASR + 台词对齐（准确文本 + 精确时间戳）
 长视频 ──┬───────┘
          ├─→ 阶段1: 场景检测 + 黑白屏检测 (ffmpeg) → 镜头时间戳列表
          ├─→ 阶段3: 抽帧 + 视觉理解 → 画面描述 + A~E 分类
          │
          ▼
  阶段4: 时间轴索引（每视频一份 JSON）
          │  多视频任务：按 seq 拼接为任务全局时间轴（offset 表）
          ▼
  阶段5: 解说稿生成（旗舰文本 LLM，每句引用精确时间区间）
          │  ▣ 闸口1：解说稿 Markdown 人工评审
          ▼
  阶段6: 选片段（E→A 优先级）+ VLM 自检回环 → EDL
          │  ▣ 闸口2：分镜板 / 粗剪版人工评审（可插入 raw_insert 高光段）
          ▼
  阶段7: 合成（一个 EDL，两个导出器）
          ├── 导出器A: ffmpeg 直出 MP4（默认，无人值守）
          └── 导出器B: 剪映草稿（人工精修通道）
```

## 4. 阶段详细设计

### 阶段 1：镜头切分（逻辑切分，不动原视频）

- 工具：ffmpeg 场景检测 `select='gt(scene,0.3)'`（阈值可调）
- 产出：**镜头时间戳列表**（JSON），不产出任何视频碎片
- 同时跑 **黑/白屏检测**（ffmpeg `blackdetect` 或帧均值像素分析）——E 类画面的廉价高置信信号
- 镜头后处理：过短（<0.5s）并入相邻镜头；超长（>60s）按固定间隔二次细分

```json
{
  "shots": [{"id": 1, "start": 0.000, "end": 4.520}],
  "fades": [{"type": "black", "start": 123.4, "end": 125.1}]
}
```

### 阶段 2：ASR + 台词对齐（本方案的关键创新点）

**问题**：ASR 对专有名词失真，但时间戳可靠；手头的准确台词无时间信息。

**方案**：序列对齐，各取所长。

1. faster-whisper 跑全片，取**词级时间戳**（文本准确度无所谓）
2. 准确台词与 ASR 转录做**字符级序列对齐**（difflib / 编辑距离 / LCS）
   - 前提成立的原因：两边是同一段内容的两种文本，顺序一致、内容高度相似；ASR 错误是局部零散的，对齐锚点充足
3. 对上的台词行继承起止时间；未对上的行在前后锚点间按字符数比例插值
4. 产出：**带精确时间戳的干净台词表**

```json
{
  "lines": [
    {"id": 1, "start": 12.30, "end": 15.80, "text": "准确台词原文", "align": "matched"},
    {"id": 2, "start": 16.10, "end": 19.40, "text": "...", "align": "interpolated"}
  ]
}
```

**多视频任务的对齐**：若一份台词横跨多个视频，将各视频音频按 seq 逻辑串联，整份台词对**任务全局时间轴**一次对齐——对齐算法不在乎音频来自几个文件。这比人工按视频拆台词更稳（拆错全错）。

**备选路线**（了解即可）：强制对齐工具（aeneas / MFA）直接对齐音频+准确文本，跳过 ASR。中文鲁棒性待验证，作为对照实验保留。

### 阶段 3：抽帧 + 视觉理解

**自适应抽帧密度**：

| 段落类型 | 抽帧策略 | 理由 |
|---------|---------|------|
| 台词密集段 | 每镜头 2~3 帧（头/中/尾） | 剧情由台词承载，帧只负责画面分类 |
| 无台词静默段 | 加密至 0.5~1 fps | 此处故事只能由画面讲述，且是 D/E 类高价值画面富矿 |

**视觉 LLM 逐镜头产出结构化标签**：

```json
{
  "shot_id": 2,
  "description": "两名角色在开阔场景对峙，镜头缓慢推近",
  "has_ui": false,
  "has_dialogue": true,
  "motion": "medium",
  "suggested_class": "B"
}
```

**A~E 分类判定规则**（多信号融合，非单一模型判断）：

| 级别 | 判定条件 |
|------|---------|
| E | 起止处有黑/白屏区间（阶段1信号）**且** VLM 判定无 UI 无台词头像 → 高置信 |
| D | 无台词行覆盖（阶段2信号）且 VLM 判定无 UI 且有运镜/动作 |
| C | 有台词覆盖 且 VLM 判定高动态/快节奏画面（帧差运动强度可辅助） |
| B | 有台词覆盖 且 VLM 判定有运镜或角色动作 |
| A | 有台词覆盖 且 VLM 判定静态对话（头像/立绘/固定机位） |

**降本手段**：多帧拼 3×3 宫格图减少调用次数；视觉模型用便宜档位即可（只回答分类与描述，非高难度推理）。

**备选路线**：mimo-v2-omni 与 qwen3.8-max 均原生支持视频输入（含音轨），分段上传直接产出带时间戳的场景描述，省掉抽帧。代价：单价高、长视频需分段、时间戳精度略飘。小样本 A/B 对比后定夺。

### 阶段 4：时间轴索引（核心数据资产）

- 合并阶段 1~3 产出，形成**每视频一份**的 timeline.json
- 由文本 LLM 将相邻镜头归并为**场景**（scene），形成「镜头 → 场景 → 全片」层级
- **多视频任务合流**：进入阶段5 前，按 `task_map.seq` 把多个视频的索引拼成一条**任务全局时间轴**，内部维护 offset 表（video1 = [0, L1)，video2 = [L1, L1+L2)…）。阶段5/6 只看到一条连续时间轴；裁切时按 offset 换算回 `(video_id, 本地时间)`

### 阶段 5：解说稿生成

- 输入：任务全局时间轴索引（台词全文 + 镜头描述，均带时间戳）
- 模型：glm-5.3（1M 上下文，选型见第5章）；稳定 JSON 结构化输出
- 篇幅控制：中文解说约 250~300 字/分钟。**时长策略（软目标）**：任务级 `target_minutes`（默认 15）指**解说正片预算，不含 raw_insert**；raw_insert 额外叠加，成片超出弹性上限（默认 target+3 分钟）时闸口2 告警，由人决定删减。（二期事项：平台时长限制的分发切分，如小红书 15 分钟上限拆多集——当前不设计）
- **风格定位**：目标受众为剧情党——**解说人格活泼、有情绪温度，但不加主观点评/吐槽**；事实层（情节、人名、因果）必须忠于台词与索引，人格只体现在措辞节奏上。全程第三人称（素材为多段实录拼接，代入视角易穿帮）。闸口1 验收尺：每句解说必须能答出「事实依据是哪条台词/哪个镜头」
- 输出：解说稿，**每句携带引用 ID（而非直接写秒数）**——LLM 只输出 `related_line_ids` / `scene_ids`，`time_range` 由管线从索引解析补写（防伪：LLM 无权写秒数，从结构上消灭编造时间戳的故障）；闸口1 前自动校验：ID 必须存在、区间必须非空，不过则打回重生成

```json
{
  "narration": [
    {"id": 1, "text": "故事始于主角在废墟中醒来……", "related_line_ids": [1, 2, 3], "scene_ids": [1]}
  ]
}
```

**关键约束**：写稿只关心故事完整性（起因/转折/结局），不为画面妥协。这从结构上消灭了旧方案的「匹配失败」。

**闸口 1（人工评审）**：解说稿渲染为 Markdown（解说句 + 时间区间 + 引用台词）供审阅。改文字、删句、调序都是改文本，重跑成本仅一次 LLM 调用。**打回意见为自由文本**（如「第二章节奏太拖，压缩一半」），重写时「原稿 + 意见 + 时间轴索引」一起给 LLM 出新稿。

### 阶段 6：选片段（E→A 优先级）+ 自检回环

**选取算法**（对解说稿每一句）：

1. 取该句时间区间，收集与区间重叠（含同场景相邻）的全部镜头作为候选池
2. **复用排除**：剔除已被 `footage_usage` 登记占用的源区间（见下）
3. 候选按 **E→A 画面优先级**排序，同级按与句意相关度（LLM 判断）排序
4. **时长匹配**：目标时长 = 该句 TTS 实际时长；首选镜头不足则串联同场景次优镜头；过长则在镜头边界截断
5. **音轨策略**：正片默认**弃原声**（避免与解说打架），解说 + BGM 覆盖；例外见 `raw_insert`

**片段使用登记（防过场复用）**：

- 台账加表 `footage_usage: video_id, shot_id, task_id`——片段一旦进入某任务的最终 EDL，**按整个镜头（shot）登记占用**，非按实际使用秒数（同一过场切不同秒数，观感上仍是重复）
- 选片阶段排除一切与已登记区间重叠的候选：**同一源画面在所有成片中只许出现一次**（任务内同理：同一 EDL 内片段源区间不得重叠）
- 豁免：通用/特殊片头（assets 引用，本就为复用而生）
- 冲突兜底：候选被占用耗尽时标记人工复核，闸口2 可强制放行（特例场景）

**EDL 片段类型**：

```json
{"type": "narration_clip", "text": "解说句", "video_id": "gs-043", "start": 95.2, "end": 108.6, "keep_audio": false}
{"type": "raw_insert", "video_id": "gs-043", "start": 1823.5, "end": 1901.2, "keep_audio": true, "note": "高光：处刑演出"}
```

`raw_insert`（原声高光段）：人工在闸口2 指定「此处直接用原始画面+原始音频」。典型用法：解说概括铺垫（放狠话）→ raw_insert 原声演出（战斗）→ 解说继续概括（战后斗嘴），后续内容随相对时间轴自动后延。**解说让位规则：raw_insert 区间不排任何解说句，EDL 校验解说片段与 raw_insert 时间不得重叠**；插入时若与既有解说句冲突，管线提示调整。**插入/调整导致后续整体后移是零成本的**——相对时间轴铁律保证 EDL 只记录片段顺序与源内时间区间，成片时间轴渲染时累积求和。

**自检回环**（旧方案缺失的反馈机制）：

- 每个选中片段抽 2~3 帧回问视觉 LLM：「这段画面是否匹配这句解说？」
- 不匹配 → 候选池取下一个重试；候选耗尽 → 标记人工复核

**闸口 2（人工评审）**：两级预览手段——

| 预览形式 | 成本 | 用途 |
|---------|------|------|
| 分镜板（单文件 HTML） | 几乎为零 | 每片段 2~3 帧 + 解说句 + 时间码一页铺开；可点选候选池替代镜头、插入 raw_insert |
| 低清粗剪版（rough cut） | 分钟级 | ffmpeg 低分辨率快拼 + 临时配音，审节奏/衔接/高光段过渡。仅重点视频启用 |

- 分镜板是**固化的 HTML+JS 查看器**：一次开发全部复用，每次仅注入 JSON（脚本内联成自包含单文件，双击即开）。**禁止让 LLM 每次生成 HTML**——LLM 负责理解，不负责渲染
- **预览必须应用与成片一致的画面变换**（见阶段7 transform），审的和出的一致，评审才有意义
- 人工调整落在 EDL：换镜头、调区间、改句子、插高光段。**管线按片段幂等**——改一句只重切该段再拼接，返工成本正比于改动量而非全片

### 阶段 7：裁切 + TTS + 合成

**裁切规则（下刀三原则）**：

1. **话优先**：起止点落在台词行边界上，一句话绝不截断（一个片段内含多个镜头是正常的）
2. **落点吸附**：多个候选落点时选靠近镜头切换点的；片段衔接尽量发生在镜头边界
3. **留缓冲**：首尾各留约 0.3s，避免切到字头气口，吸收 TTS 与画面的时长误差

**画面变换（裁 LOGO）**——系列级渲染预设：

```yaml
transform: {scale: 1.10, offset_y: -40}   # 放大110%、上移40px，LOGO 区出画
```

- 导出器A：ffmpeg `crop`/`scale` 滤镜链统一应用；个别镜头 LOGO 位置不同允许 per-clip 覆盖
- 导出器B：剪映草稿片段自带 scale/position 属性，同样写入
- 闸口2 预览同样应用此变换

**音轨模型（三条独立轨）**：

| 轨道 | 内容 | 规则 |
|------|------|------|
| 解说轨 | TTS 逐句合成 | 逐句量时长，回供阶段6 时长匹配 |
| BGM 轨 | **任务级人工指定歌单**（task.json `bgm_playlist`，必填；音乐须与剧情地区/氛围相符，不做自动匹配、不做系列级默认） | 按清单顺序铺设、放完循环；单曲间及循环接缝 2s 交叉淡化（crossfade）；ducking 闪避：先用固定 -12~-15dB，听感不行再上 `sidechaincompress`；raw_insert 段自动再压低或暂停 |
| 画面轨 | 原视频片段 | 默认 `-an` 弃原声；`keep_audio: true` 的 raw_insert 段保留原声 |

**组合模板（片头结构）**——任务/系列级配置：

```yaml
# task.json
composition:
  - {type: intro_common,  src: assets/intros/common.mp4}   # 通用片头
  - {type: intro_special, src: assets/intros/gs-4.3.mp4}   # 本任务特殊片头
  - {type: body}                                           # 解说稿正片（EDL）
```

**字幕（硬字幕为主，软字幕白送）**：

- **解说字幕**：TTS 须选支持 **word boundary（字级时间回调）** 的服务 → 每个字时刻精确已知，字幕与声音天然对轴。断行双保险：LLM 写稿时输出建议断行点（语义最优）→ 管线硬性校验兜底（标点优先 > 语义 > 字数均衡，不切断词语）
- **raw_insert 原台词字幕**：复用阶段2 的 ASR 词级时间戳 + 台词对齐成果，零新增成本
- **渲染**：硬字幕烧录进画面 + 软字幕轨（srt）顺手封装。**字幕模式为系列级配置 `subtitle_mode`，二选一**：
  - `letterbox`（黑边模式）：上下裁切出电影画幅，底部 UI 区被黑边遮罩，解说字幕烧在下黑边上；与 E 类过场原生黑边天然融合，全片画幅统一；与 transform 共用滤镜链需联调；分镜板预览按最终画幅渲染
  - `overlay`（白边描边，默认）：解说字幕加白边/底色直接压住游戏原字幕，不损失画面，实现最简单
- **「UI」定义澄清**：分类信号中的 UI 包含常驻界面元素（血条/小地图/任务追踪）**及游戏对话框**——纯对话镜头因此自然落入 A/B 类
- **参数基线**：每屏 ≤18 字、单屏停留 1.0~6.0s、≤2 行；字数上限与语速联动（语速调快则上限调低），配置里写明联动关系

**合成（一个 EDL，两个导出器）**：

- **导出器A（默认）**：TTS 解说音轨 → ffmpeg 按 EDL 临时切片段（应用 transform）→ 片头+正片按 composition 拼接 → 叠加解说/BGM 音轨 → 可选字幕/转场 → 成片 MP4（文件名由命名模板渲染）+ 归档 EDL
- **导出器B（精修）**：生成剪映专业版草稿（草稿 = 目录 + `draft_content.json`，公开 JSON 结构，可用 pyJianYingDraft 等社区库程序化生成：片段排列、字幕、转场、BGM 轨）。人工在剪映中加音乐、调字幕样式、微调切点后手动导出
- Premiere 作为二期选项（FCPXML/XML 导入或 OpenTimelineIO 中转）
- **单向数据流**：剪映是终点——导出那一刻归档 EDL 并登记 footage_usage（以导出时 EDL 为准），剪映内手调不回流、不同步。接受了 footage_usage 的小误差（手调删掉的片段被多登记，仅损失候选池容量）；需在剪映大改的稀有场景，回闸口改 EDL 重导
- 分工原则：**大问题在闸口改 EDL 重跑（便宜），小问题进剪映手调（不重跑管线）**

## 5. 外围依赖

**规模前提**：约 500 个视频 × 平均 3 小时 ≈ 1500 小时素材，基本不跨视频调用素材（一部或一组视频产出一部解说片）。

| 组件 | 选型 | 说明 |
|------|------|------|
| ffmpeg | — | 场景检测、黑白屏检测、裁切、变换、合成，全部体力活 |
| ASR | **faster-whisper**（Python 库，本地运行，`word_timestamps=True` 词级时间戳为硬指标） | 只当钟用不当文本源 → **可降级 medium/small 模型提速数倍**，时间戳精度几乎不变。1500 小时总量若单机过慢，备选：云 ASR（约 ¥1~2/小时）或 MiMo-V2.5-ASR |
| 文本 LLM（写稿） | **glm-5.3**（1M 上下文，文本-only 最便宜，$1/$4） | 全场唯一需要旗舰模型的环节；写稿输入是纯文本索引，无需视觉。备选 kimi-k3 / qwen3.8-max（均 1M） |
| 视觉 LLM（抽帧+自检） | **mimo-v2-omni**（262K 上下文，图/视频/音频输入，$0.40/$2） | 全项目调用量最大环节（500 片 × 约 800~1000 次 ≈ 40~50 万次），必须用便宜档。备选 qwen3.7-plus |
| 文本杂活（场景归并、候选排序） | deepseek-v4-flash / glm-5.1 | 便宜文本模型即可 |
| TTS | **火山引擎（豆包）/ 阿里云**（中文音色、SSML 完善） | 逐句合成、逐句量时长，任何 TTS 天然满足。500 片 × 约 4000 字 ≈ 200 万字，云服务成本数百元级。本地零成本备选：CosyVoice2 / GPT-SoVITS；可先行试用 MiMo-V2.5-TTS。**音色按系列固定**（写进类型适配层，任务继承可覆盖）；语速默认 1.1 起步，粗剪版听感验收后再调 |
| 素材索引存储 | **JSON 文件**（每视频一份，共数 GB） | 不跨视频检索，JSON 仍是正确形态 |
| 台账 | **SQLite 单文件，两本账**（见下） | 500 片规模新增的需求是编排与登记，而非关系型存储 |

**台账设计（一个 SQLite 文件，两本账，职责分离）**：

| 台账 | 面向 | 内容 | 谁来写 |
|------|------|------|--------|
| 执行台账（`jobs` 表） | 机器 | stage、status、retry_count、断点续跑 | 管线自动写，易失 |
| 素材台账（`catalog` + `task_map` 表） | 人 | video_id ↔ task_id 映射、系列、版本号、章节名 | 人维护，业务资产（二期素材库的种子） |

```sql
catalog:  video_id, series, version, chapter, source_path, script_path
--        gs-043    原神    4.3      罪人舞步旋   ...
task_map: task_id, video_id, seq      -- 一个任务可引用多个视频；seq 人工指定（task create 时的视频顺序），管线不做自动推断
jobs:     task_id, stage, status, retry_count, updated_at
footage_usage: video_id, shot_id, task_id   -- 片段使用登记（镜头级），防跨成片复用
```

- **video_id 不编码含义**：版本/章节用语义字段承载，编码进 ID 会随改名埋雷
- **录入入口**：人编辑 YAML/CSV 清单（500 行好填好审），管线启动时导入 `catalog` 表
- **成片命名走模板**：`title_template: "第{version}版本-任务：{chapter}"`，按系列配置；模板即类型适配层的一部分
- **未来**多机并行 + 管理后台时，表结构原样平迁 MySQL

**检索手段（500 片规模下按 task_id 快速定位）**：

| 手段 | 形态 | 用途 |
|------|------|------|
| CLI 直查（主力） | `mmm locate <task_id>` 打印全部关联路径；`--open` 打开目录；`mmm find <关键词>` 按章节名/版本号模糊查 | 毫秒级，SQL 藏在命令后 |
| 目录名即 task_id | `tasks/{task_id}/`、`output/{task_id}/` | 记得住的任务无需查，直接 cd |
| 符号链接视图 | `output/_by_series/{系列}/{标题}.mp4 -> ...` | Finder 浏览用；台账自动渲染的**投影**，永不手工编辑，不一致时删掉重建 |

**原则**：台账是唯一事实源，目录名与链接视图都是它的投影——所有入口从同一张表生成。

**明确不需要**：向量数据库（稿画对齐靠时间戳，无模糊检索需求；二期做跨视频素材库时再议）、MySQL（见上）。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 台词与视频版本不一致（配音改动/剪辑） | 对齐大面积失败 | 对齐阶段输出覆盖率报告；低于阈值（如 85%）报警转人工 |
| 多视频任务的素材/台词顺序错误 | 全局时间轴错乱，全片错位 | task_map.seq 显式声明；对齐覆盖率按视频分段报告，异常段定位到具体视频 |
| 场景检测阈值不当 | 镜头过碎/过粗 | 阈值可配置；后处理合并/细分；调整只重算元数据，不动原视频 |
| 视觉分类误判（UI 检测、E 类漏检） | 选片质量下降 | 多信号融合判定；自检回环拦截；闸口2 人工替换 |
| LOGO 位置随版本漂移 | transform 裁不干净或误裁 | transform 支持 per-clip 覆盖；闸口2 预览应用同样变换，问题在评审期暴露 |
| raw_insert 与原声/解说衔接突兀 | 听感跳变 | BGM 在插入段自动闪避；粗剪版重点审衔接 |
| 长视频超出文本 LLM 上下文 | 无法一次写稿 | 按场景分段摘要后二次汇总；glm-5.3 的 1M 上下文对 3 小时素材余量充足 |
| TTS 时长与画面不匹配 | 音画错位 | 逐句时长回报 + 片段伸缩规则 + 0.3s 缓冲 |

## 8. 关键设计决策记录（ADR 摘要）

1. **为什么不用 ASR 文本做内容？** ASR 时间可靠、文本不可靠（专有名词）；手上有准确台词，序列对齐让两者各取所长。
2. **为什么不物理切分视频？** 镜头是逻辑单位；物理碎片制造冗余 I/O，且任何参数调整都要重切几小时原片。
3. **为什么先写稿后选画面？** 倒过来做（画面决定故事）就是旧方案失败的根本原因。
4. **为什么不要向量库？** 稿画对齐的锚是时间戳不是语义，本方案无模糊检索场景。
5. **为什么 E 类用黑白屏检测而非纯 VLM？** 像素级信号廉价且接近零误判，VLM 只做确认，成本与准确率双优。
6. **为什么模型按环节配档位？** 写稿要 1M 上下文旗舰（glm-5.3），抽帧要便宜视觉（mimo-v2-omni），杂活用廉价文本（deepseek-v4-flash）——全流程成本由调用量最大的环节决定，旗舰只花在刀刃上。
7. **为什么 500 片规模仍不上 MySQL？** 规模改变的是编排（状态/重试/断点续跑）与登记（素材台账），不是存储；不跨视频检索就没有关系型需求。SQLite 零部署且表结构可平迁。
8. **为什么全管线禁止绝对成片时间（相对时间轴铁律）？** raw_insert 插入、片段调整会改变后续一切的时间坐标；EDL 只记 `(video_id, 源内区间)` + 片段顺序，渲染时累积求和——后续后移零成本，这是支持人工自由调整的前提。
9. **为什么多视频任务用全局时间轴 + offset 表，而不是各视频独立处理？** 解说稿是章节级的，写稿必须看到完整故事；合流点放在阶段5 之前，阶段5/6 对多视频完全无感，裁切时才换算回源文件坐标。

## 9. 工程目录结构

三类资产分离：**输入源（素材库，只读）→ 半成品（可重建）→ 成品**。另以「任务」维度组织产出——一部成片对应一个任务，一个任务可引用一个或一组视频。

```
movie/
├── .claude/
│   └── skills/
│       └── mini-movie-maker/        # Skill 薄层（验收后人工晋升全局 ~/.claude/skills/）
│           ├── SKILL.md             # 流程指引 + 闸口协议 + 命令手册（读者是 Agent）
│           ├── references/          # EDL schema、台账表结构、系列配置示例
│           └── tools/               # 分镜板固化 HTML+JS（reviewer）
│
├── docs/                          # 文档
├── CONTEXT.md                     # 术语表
├── src/                           # 管线本体代码（mmm CLI，Python）
├── catalog.yaml                   # 素材台账录入入口（人维护，导入 SQLite）
│
├── materials/                     # 【输入源】素材库，只读，管线禁止写入
│   └── {video_id}/
│       ├── source.mp4             # 原视频
│       └── script.jsonl           # 准确台词（JSONL，格式见物料规范）
│
├── assets/                        # 【输入源】系列级共享素材（只读）
│   ├── intros/                    # 通用/特殊片头
│   └── bgm/                       # 背景音乐库
│
├── config/
│   └── series/                    # 类型适配层：分级表、命名模板、composition、transform、subtitle_mode、TTS 音色
│
├── workspace/                     # 【半成品】中间产物，可删可重建
│   └── {video_id}/
│       ├── shots.json             # 阶段1：镜头时间戳列表
│       ├── fades.json             # 阶段1：黑白屏区间
│       ├── asr.json               # 阶段2：ASR 原始转录（仅取时间戳）
│       ├── lines.json             # 阶段2：对齐后的干净台词表
│       ├── frames/                # 阶段3：抽帧图片（消耗品，用完可删）
│       ├── shots_meta.json        # 阶段3：镜头视觉标签（A~E 分类等）
│       └── timeline.json          # 阶段4：时间轴索引（核心数据资产）
│
├── tasks/                         # 【任务】一部成片 = 一个任务
│   └── {task_id}/
│       ├── task.json              # 任务定义：引用 video_id 列表(seq)、命名模板、composition、transform、subtitle_mode、bgm_playlist、target_minutes
│       ├── global_timeline.json   # 阶段4.5：任务全局时间轴（多视频合流 + offset 表）
│       ├── narration.json         # 阶段5：解说稿 → 闸口1 审阅对象
│       ├── edl.json               # 阶段6：剪辑决策清单 → 闸口2 审阅/调整对象
│       └── preview/
│           ├── storyboard.html    # 分镜板（自包含单文件，双击即开）
│           └── roughcut.mp4       # 低清粗剪版（可选，重点视频启用）
│
├── output/                        # 【成品】
│   ├── {task_id}/
│   │   ├── {标题}.mp4             # 导出器A：成片，文件名由命名模板渲染
│   │   ├── jianying_draft/        # 导出器B：剪映草稿工程（单向终点，不回流）
│   │   └── edl.final.json         # 归档的最终决策清单（复盘/二期素材库用）
│   └── _by_series/                # 符号链接视图（台账投影，可删可重建）
│       └── {系列}/{标题}.mp4 -> ../{task_id}/{标题}.mp4
│
└── pipeline.sqlite                # 台账：catalog + task_map + jobs + footage_usage 四表
```

**设计要点**：

- `materials/` 与 `assets/` 全程只读——「文件只在必须时诞生」，原视频永不被修改
- `workspace/` 整体可删：任何一层产物都能从上一层重算，删除不影响成品
- `frames/` 是最大的消耗品目录，视觉理解完成后即可清理
- `tasks/` 与 `workspace/` 分离的原因：索引按视频建（workspace），解说稿/EDL/成片按任务走（tasks），合流点是 `global_timeline.json`
- `pipeline.sqlite` 是唯一事实源；`catalog.yaml` 是人的录入入口，`_by_series/` 是台账的投影——三者冲突时以 SQLite 为准，后两者均可重建
- 检索入口：`mmm locate <task_id>` 直查全部关联路径（`--open` 打开目录）；`mmm find <关键词>` 按系列/版本/章节名模糊查

## 10. 人的参与点与界面

**原则：人只做三件事——登记、评审、精修（可选）。其余时间管线自动跑，异常才来找人。** 默认无人值守，两个闸口是仅有的主动参与点。

### 旅程总览

```
①登记素材  →  ②建任务  →  ③管线自动跑(阶段1~4)  →  ④闸口1审稿  →  ⑤闸口2审片  →  ⑥出片/精修
 几分钟/批      一条命令      人不在场，异常才叫       主动参与      主动参与      可选参与
```

### 各环节界面

| 环节 | 界面形态 | 人看到/做什么 |
|------|---------|--------------|
| ① 登记素材 | CLI `mmm add` + `catalog.yaml` | 丢文件、一条命令登记；CLI 回显确认与台词预检结果 |
| ② 建任务 | CLI `mmm task create` | 引用视频、选系列模板；回显组合/transform/目标时长 |
| ③ 自动跑（阶段1~4） | CLI `mmm run` + `mmm status` | 人不在场。status 显示「任务×阶段」进度表，失败标红附原因；异常（对齐覆盖率过低、缺台词）通过 macOS 系统通知 + status 标红找人 |
| ④ 闸口1 审稿 | 本地固化 HTML 审稿页 | 左侧解说稿可直接改字，右侧时间区间与引用台词；每部片「通过 / 打回（附意见，LLM 按意见重写）」 |
| ⑤ 闸口2 审片 | 分镜板 storyboard.html | 片段网格：帧图 + E~A 分级徽章 + 解说句；操作：候选池换镜头、插入 raw_insert 高光段、拖调起止点；可重新生成粗剪版看衔接；通过 → 进合成队列 |
| ⑥ 出片/精修 | Finder（`_by_series/` 视图）+ 剪映 | 直出片直接可用；需精修的打开 jianying_draft 进剪映手调 |
| 日常管理 | CLI `status / locate / find` | 进度总览、路径直查、关键词模糊检索 |

**关键机制：待审队列。** 500 片分批审——队列进度存在台账里，审一部销一部，支持「今天十部、明天十部」的节奏。

**刻意不做**：Web 后台。单机单人规模下 CLI + 静态 HTML 全覆盖；Web 服务是二期规模化选项。

## 11. mini-movie-maker Skill 设计

**定位**：管线沉淀为 Claude Code Skill，供 Agent 调用。读者是 Agent——SKILL.md 写清流程与闸口协议，任何接手的 Agent 都知道「跑到闸口就停，人来审，审完继续」。

**存放**：项目内 `.claude/skills/mini-movie-maker/`（验收成熟后由人手动晋升到全局 `~/.claude/skills/`）。

### 技术选型

- **语言：Python 3.11+**——全部依赖不出 Python 生态：faster-whisper（ASR）、difflib（对齐，标准库）、sqlite3（台账，标准库）、pyJianYingDraft（剪映草稿）、火山/阿里 TTS SDK、ffmpeg 走 subprocess
- CLI 框架 `typer`；依赖控制在一屏以内
- 命令名 `mmm`（mini-movie-maker 缩写）

### 结构

```
.claude/skills/mini-movie-maker/
├── SKILL.md                  # 触发条件、七阶段流程、闸口协议、命令手册
├── references/               # EDL schema、台账表结构、类型适配层配置示例
└── tools/                    # 分镜板固化 HTML+JS（reviewer）

src/                          # 管线本体代码（mmm CLI 实现）
```

Skill 是薄层：SKILL.md + 参考资料指向项目内的 `mmm` CLI；晋升全局时连同 scripts 一起拷贝。

### 命令清单（闸口外全功能）

| 命令 | 对应阶段 | 说明 |
|------|---------|------|
| `mmm add` | 登记 | 素材入库 + 台账登记 + 台词预检 |
| `mmm task create` | 建任务 | 引用视频、选系列模板 |
| `mmm run shots / align / vision / index` | 阶段1~4 | 可分阶段跑，可 `--all` 连跑；jobs 台账记录断点 |
| `mmm run narrate` | 阶段5 | 生成解说稿 + Markdown 评审稿 |
| `mmm run select` | 阶段6 | 选片 + 自检回环 + 生成 storyboard.html |
| `mmm run render` | 阶段7 | 导出器A 直出 MP4 |
| `mmm export jianying` | 阶段7 | 导出器B 剪映草稿 |
| `mmm status / locate / find` | 管理 | 进度表 / 路径直查 / 模糊检索 |

### 闸口协议（SKILL.md 核心条款）

1. 阶段5 完成后，Agent 生成评审稿，**必须停下**，通知人审 `narration.md`，不得擅自进阶段6
2. 阶段6 完成后，Agent 生成 storyboard.html，**必须停下**，等人审完（人可能改了 edl.json）
3. 人口头确认「通过」即闸门开关；Agent 校验产物后继续
4. Agent 可以替人做的：读打回意见、重跑受影响片段、解释某镜头为什么被选中
