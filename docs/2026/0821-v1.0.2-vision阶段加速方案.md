# Vision 阶段加速方案 v1.0.2

> 版本：v1.0.2
> 日期：2026-08-21
> 背景：vision（阶段3 视觉理解）单次全量耗时过长——939 镜头需 ~10 小时，"为十几分钟成片做一天准备"严重不合理。本方案给出从调用次数、并发、采样三层压缩，将全量耗时降到 ~25 分钟。
> 关联：设计文档 `docs/2026/0817-长视频浓缩工作流.md` §4 阶段3；PROGRESS 待办 P3-10（宫格拼图降本）、P3-11（自适应抽帧）的落地实现。

## 1. 问题量化（基于实测）

### 1.1 瓶颈实测

| 测量项 | 实测值 | 方法 |
|--------|--------|------|
| 单次 VLM 调用耗时 | 13~20s（中位 ~16.6s） | `chat_with_image('mimo-v2.5', ...)` 计时，连测 2 次 |
| 每镜头调用次数 | 3 次（头/中/尾三帧独立调用） | `analyze_shot` 代码实读 |
| 镜头间/帧间调用方式 | 全串行 | `run` 主循环 + `analyze_shot` 内层循环 |
| LLM 节流 | 0.5s/调用（全局 `_last_call`） | `llm.py` `MIN_INTERVAL_SEC` |

**现状账**（939 镜头全量）：

```
939 镜头 × 3 次/镜头 × ~16s/次 = ~45000s ≈ 12.5 小时（纯串行）
减去 P1 已完成 273，待跑 666：666 × 3 × 16s ≈ 9 小时
```

与首次后台任务观察吻合（每镜头 1~1.5 分钟）。

### 1.2 根因排序（按贡献）

| # | 根因 | 性质 | 可优化空间 |
|---|------|------|-----------|
| 1 | **每镜头 3 次独立调用** | 设计冗余 | ×3（头中尾合一次） |
| 2 | **全链路串行** | 实现缺陷 | ×6~8（网关实测不限频） |
| 3 | mimo-v2.5 思考型单次 13~20s | 模型选型（质量已验证，不动） | 常数 |
| 4 | 抽帧 ffmpeg | 每次 <1s | 忽略 |

**讽刺点**：`llm.py` 注释自述"实测 zen 网关不限频率，限速仅防突发并发"——但 vision 从未并发过。

## 2. 优化原则

- 不降低分类信号质量（has_ui / has_dialogue_scene / motion / is_cutscene），下游 index/narrate/select 无感知
- schema 不变，已完成镜头可与新格式镜头混用（断点续跑零损失）
- 短镜头（<2s）在选片层本就该废弃（成片频繁跳切致眩晕），与其调 VLM 不如直接跳过
- 并发有界（默认 6），网关 5xx/429 由 `llm.py` 现有指数退避兜底

---

## 3. 优化层

### 层 1：三帧拼图 → 1 次调用（调用量降 67%）

镜头区间内仍抽头/中/尾三帧，但用 ffmpeg `hstack` 横向拼成**一张三格图**，一次 VLM 调用分析整张拼图。

```
旧：[抽头帧]→[VLM] [抽中帧]→[VLM] [抽尾帧]→[VLM] → 三结果并集/交集融合
新：[抽头/中/尾]→[hstack 拼图]→[VLM 一次] → 镜头级结论
```

**prompt 调整**（必须）：从"这是一帧画面"改为"这是同一镜头头/中/尾三格、从左到右时间顺序、对整个镜头输出一个标签"。输出 JSON 字段不变，语义从单帧判定升级为镜头级综合判定。

**附带收益**：省掉 `analyze_shot` 里多帧并集/交集融合逻辑（has_ui any / motion max / is_cutscene all），拼图一次出镜头级结论，更直接；长镜头头中尾画面变化大时，拼图让 VLM 一次看全时序演变，描述反而更准（见 §5 验证）。

### 层 2：并发调用（×6 加速）

`run` 主循环改 `ThreadPoolExecutor(max_workers=6)`，镜头级并发。每镜头结果按 `shot_id` 收集到 dict 再排序落盘，线程安全。

- 环境变量 `MMM_VISION_WORKERS`（默认 6）可调
- 配套环境变量 `MMM_LLM_INTERVAL=0.05` 放宽节流（默认 0.5s 在并发下会成为隐式串行瓶颈——6 线程错峰后 0.5s 间隔=2 req/s 上限，6 workers 各 ~16s/次 → 平均 0.4 req/s 不构成瓶颈，但放宽更稳）
- `llm.py` 现有 30s→300s 指数退避应对偶发 5xx/429

### 层 3：≤2s 镜头废弃（省 ~10~22% 调用 + 成片体验）

镜头时长 < `MIN_SHOT_DUR`（默认 2.0s，env `MMM_VISION_MIN_DUR`）：

- **vision 阶段**：跳过 VLM 调用，写 `_skip: "short"` 标记 meta（给保守低分级数据让 index 不报错）
- **select 阶段**：`_collect_candidates` 加 `duration < 2.0` 排除（双保险，对历史数据也生效）

**产品依据**：≤2s 镜头切到成片里频繁跳切会让观众眩晕，本就该排除；与其浪费调用给它们打标签，不如直接废弃。

### 镜头时长分布（实测，939 镜头）

| 时长桶 | 数量 | 占比 |
|--------|------|------|
| ≤1s | 18 | 2% |
| 1~3s | 227 | 24% |
| 3~6s | 377 | 40% |
| 6~10s | 200 | 21% |
| 10~20s | 65 | 7% |
| >20s | 52 | 6% |

## 6. 风险与权衡

- **拼图描述精度**：单图比三独立调用信息略集中，长镜头（>10s）反而更准；极短镜头已废弃，不影响。
- **并发网关压力**：默认 6 保守，实测 0 失败。可调高 `MMM_VISION_WORKERS` 试 8~12，若现 429 退避会自动降速。不建议 >16。
- **≤2s 废弃的兜底**：若某解说句区间只有 ≤2s 镜头可选，select 的 `_collect_candidates` 会候选耗尽触发兜底（标 `needs_review`，闸口2 人工复核）。极端情况可接受。
- **历史镜头混用**：旧格式（3帧融合）与新格式（拼图1次）schema 一致，下游无感知。重跑时旧镜头默认复用不覆盖；如需全量用新格式，删 `shots_meta/` 后 `--force`。
- **`llm.py` 全局 `_last_call` 竞态**：多线程下偶有 sleep 误差，无害；`MMM_LLM_INTERVAL=0.05` 后基本不 sleep。
