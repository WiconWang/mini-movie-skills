# 解说稿大输入优化方案（5–10 视频合一篇）

> 日期：2026-08-20
> 背景：当前 `stage_narrate.py` 把单任务全部台词行 + 镜头一次性拼进 prompt 交给 LLM。单视频已到 24k tokens，5–10 视频合一篇预计 120k–240k tokens，思考型模型（deepseek-v4-flash）会推理耗尽输出预算导致**空稿/超时**（已复现）。本方案给出从时间轴生成到交 LLM 的端到端优化。

---

## 1. 问题量化（基于 hd-p1 实测）

`tasks/hd-p1/global_timeline.json` 来自**单视频** `gs-16-p1`（时长 1713s ≈ 28.5 分钟）：

| 对象 | 单视频 | 5 视频 | 10 视频 |
|------|--------|--------|---------|
| 文件体积 | 227KB | ≈1.1MB | ≈2.2MB |
| **进 prompt 字符**（lines+shots） | 36.5k | ≈182k | ≈365k |
| **进 prompt tokens**（≈1.5 字/token） | ≈24k | ≈120k | ≈240k |
| lines 条数 | 475 | ≈2375 | ≈4750 |
| shots 条数 | 273 | ≈1365 | ≈2730 |

> 注：文件 227KB 里 `fades/stats/videos` 不进 prompt（仅 `lines`+`shots` 两块被 `_build_prompt` 序列化）。所以"传给 LLM 的是 24k tokens，不是 227KB 全量"。

### 两大瓶颈

1. **推理预算耗尽（已复现）**：`NARRATE_MAX_TOKENS=32768`，deepseek-v4-flash 是思考型模型，输入越大推理烧掉越多。代码注释自述"2 万+ token 输入下推理可烧掉 8k+"。5–10 视频会直接吃光 32768 输出预算 → 正文为空或调用超时（即本次卡住现象）。
2. **叙事架构不成立**：提示词要求"15~30 个叙事单元、**完整覆盖全部台词段**"。单视频 475 行已吃力；5–10 视频要塞进 15~30 句，等于每句覆盖 80–160 行，"完整覆盖"必然退化为流水账或大面积遗漏。

**结论**：5–10 视频合一篇不能靠"单次喂全量"解决，必须**压缩（减条目）+ 分层（分治）**双管齐下。

---

## 2. 优化原则

- 不在单条 LLM 调用里塞全量；单调用输入必须**有界**（目标 ≤ 30k tokens）。
- 压缩不能破坏 `related_line_ids` 的可追溯性（后续程序靠它补时间区间、回源切片）。
- 相对时间轴铁律不变：`local_*` 始终锚定源视频。
- 分层后各阶段产物可断点续跑、可人工闸口审阅。

---

## 3. 优化层

### 层1：条目过滤与精简（per-video prompt 内，无损压缩）

实测 `hd-p1` 的 475 行构成：

```
matched(✓)=278  interpolated(~)=53  unmatched(?)=96  unvoiced(-)=48
```

- **删除 `unvoiced(-)` 行（48 条）**：无配音，提示词本就要求忽略，且不含画面信息。
- **降级 `unmatched(?)` 行（96 条）**：这些是对齐未命中的台词（剧情存在但无对应画面）。不再逐条喂入，改为在 prompt 末尾附一句极简标记："[未匹配台词区间：Xs–Ys 存在约 N 段无画面剧情]"，供模型判断"此处有剧情跳跃"即可，不消耗逐行 token。
- **shots 只保留有 `line_ids` 的（242/273）**：其余 31 条多为纯 A 类空镜/UI，对叙事贡献低；若 `class ≥ C` 且描述有信息再保留。

**实测收益**：单视频 prompt 36.5k 字符 → **≈19.6k 字符 ≈ 13k tokens（砍 45%）**。10 视频由 240k → ≈130k。

代码点：`stage_narrate._build_prompt` 增加过滤参数 `compact=True`。

### 层2：分层生成（核心，解决 5–10 视频）—— 两阶段 hierarchical

不在一条调用里写完整篇，改为：

```
5a 分片草稿（per-video）          5b 全局融合（fusion，单调用）
┌──────────┐ ┌──────────┐         ┌──────────────────────────┐
│ 视频1索引 │→│ 草稿1     │         │ 汇总 草稿1..N（小）        │
│ 视频2索引 │→│ 草稿2     │ ──────→ │ + 跨片剧情摘要            │→ 最终 narration
│  ...     │→│ ...      │         │ 统一口吻/去冗余/裁剪到目标 │
│ 视频N索引 │→│ 草稿N     │         └──────────────────────────┘
└──────────┘ └──────────┘
```

- **5a 分片草稿**：每个视频独立调用，目标时长 = 总目标 / 视频数（如 5 视频、总目标 15min → 每片 ≈3min）。输入为层1 压缩后的单视频索引（≈13k tokens），**可控、不会超时**。输出结构化 narration：`{video_id, narration:[{id,text,related_line_ids}]}`。
- **5b 全局融合**：把 N 个分片草稿（总体积小，5–15k tokens）+ 一段跨片剧情摘要，一次调用。融合职责：
  - 统一口吻、术语、人称；
  - 删除跨片重复/冗余；
  - 按总目标时长裁剪、重排；
  - 补分片边界的衔接句；
  - 输出**最终 narration**，`related_line_ids` 以 `(video_id, line_id)` 形式保留可追溯。

融合调用输入有界（≤30k），不再触发空稿/超时；分片调用各自有界。

### 层3（可选）：场景级预摘要

若单视频本身就超大（>60min），在 5a 内再按场景边界（`shots` 的 class 跃迁 / 静默段）切分，先生成 scene-summary 再写稿。对应设计文档注释"极端场景按场景切分而非行数截断"。5–10 视频常规规模下通常不需要，作为兜底。

### 层4：Token 预算与模型配置

- 分片调用 `max_tokens` 下调（如 8192，单片短稿足够）；融合调用保留大预算（如 16384）。
- 分片可用更快/更便宜的非思考模型，融合用思考模型保证一致性；或统一降 `temperature` 到 0.4 减少发散。
- `chat()` 增加**调用超时 + 进度日志**（当前无增量输出，易误判卡死）。

## 4. 代码结构改动

`src/mmm/stage_narrate.py`：

```python
# 层1：过滤版 prompt
def _build_prompt(timeline, target_minutes, *, compact=True):
    lines = [l for l in timeline["lines"]
             if l.get("align") in ("matched", "interpolated")]   # 丢 unvoiced
    # unmatched 降级为区间标记，不逐条喂
    shots = [s for s in timeline["shots"] if s.get("line_ids")]
    ...

# 层2：分片草稿（单视频索引 → 草稿）
def run_segment(timeline_path, out_dir, *, target_minutes, video_id): ...

# 层2：全局融合（多分片 → 终稿）
def fuse(per_video_dir, out_dir, *, target_minutes): ...

# 原 run() 保留为 oneshot 模式（小任务兼容）
def run(timeline_path, out_dir, *, target_minutes=15.0, mode="auto"):
    # mode=auto：多视频自动走 segment+fuse；单视频走 oneshot
```

CLI（`src/mmm/cli.py`）：

```
mmm run narrate <task_id> [--mode segment|oneshot] [-t 15]
```

中间产物：

```
tasks/{task_id}/
  narration_segments/{video_id}.json   # 层2 分片草稿
  narration.json / narration.md        # 层2 融合终稿（闸口1 审阅）
```

`related_line_ids` 在终稿中以 `{"video_id": "gs-16-p1", "line_id": 12}` 结构保留，确保 `_to_markdown` 仍能补写时间区间、回源切片。

## 5. 预期收益

| 指标 | 优化前 | 优化后（10 视频） |
|------|--------|-------------------|
| 单条调用最大输入 | 240k tokens | ≤30k tokens |
| 空稿/超时风险 | 高（已复现） | 消除 |
| 单视频 prompt | 24k tokens | 13k tokens（-45%） |
| 叙事覆盖 | 15–30 单元硬塞 4750 行 | 分片保覆盖 + 融合保一致 |
| 可追溯性 | ✅ | ✅（video_id 前缀） |

---

## 6. 风险与权衡

- **融合不一致**：分片各自成稿，口吻/术语可能漂移 → fusion prompt 须强约束"沿用统一人称与命名"。
- **删 unmatched 丢剧情**：提供开关 `keep_unmatched_as_marker=True`（默认开），以区间标记而非逐行保留。
- **分片边界割裂**：融合阶段专职补衔接句，必要时回看相邻分片首尾。
- **成本**：分层增加调用次数（N 分片 + 1 融合），但单次 token 大降，整体成本通常更低。

## 7. 验证计划

1. **层1 单视频对比**：压缩前后各生成 `hd-p1` 稿，人工闸口1 比对覆盖度与流畅度。
2. **层2 两视频端到端**：`mjzd-p2` 补齐索引后，跑 `segment`+`fuse`，核对 `related_line_ids` 可回溯到源 `video_id` 的 `local_*`。
3. **压测**：逐步扩到 5 / 10 视频，记录单次调用 token、耗时、是否空稿。
4. **回归**：`tests/test_align.py` 等既有测试不受影响（改动仅限 narrate 阶段）。
